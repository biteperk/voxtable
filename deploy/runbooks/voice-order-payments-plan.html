1. The decision, up front

Build it on Checkout Sessions, not Payment Links.

Niza's suggested workflow is architecturally right — AI extracts the order, generate a link, text it, listen for checkout.session.completed. But the primitive she named is the wrong one for a one-shot restaurant order, for a reason that has nothing to do with pricing.

A Payment Link is a permanent, reusable, shareable URL. It has no expiry and no single-use mode. If a caller forwards their fish-and-chips link to a friend, the friend pays and you get a second phantom order. A Checkout Session is single-use and expires — you set expires_at anywhere from 30 minutes to 24 hours after creation. For a link that represents one specific person's one specific meal tonight, that is the correct object.

Payment LinkCheckout Session
Single-useNo — reusable by design, no expiryYes — expires_at 30 min – 24 h, default 24 h
Inline pricingYes, price_data is supportedYes, price_data
Line items (payment mode)Max 20Max 100
Reconciliation to our ordermetadataclient_reference_id (200 chars) and metadata
Connect destination chargeSupportedSupported, documented pattern
Hosted page, wallets, RadarSameSame
Right forA deposit link, a fixed set menu, a QR code on the tableOne caller, one order, one payment

Payment Links stay useful later — a table QR code or a standing deposit link is exactly what they're for. They are just not the object for tonight's fish and chips.

2. Where the Stripe email is misleading

Three things in Niza's recap need correcting before anyone builds from it.

"You'll need to create products and prices for your menu items first"

Not true, and it's the line that would have cost the most time. Both Payment Links and Checkout Sessions accept line_items[].price_data, which generates a Price inline from currency, unit_amount and product_data.name. Nothing needs to exist in Stripe beforehand.

This matters because our menu is not a fixed price list. A line item's price is base_price_cents + variant.price_delta_cents + Σ modifier.price_delta_cents, computed per order in orderService.ts. Pre-creating a Stripe Price for every combination of size, half-serve and modifier is not a real option. With price_data we send the number we already computed and never sync a catalogue.

Correction to earlier advice. An earlier read of this concluded Payment Links accept only a pre-created price. The current API reference for POST /v1/payment_links lists line_items.price_data as a supported alternative — "One of price or price_data is required." That was true historically and is no longer. The recommendation above stands, but on the reuse/expiry argument, not the pricing one.

Missing: the delayed-settlement trap

Stripe's own Checkout guidance is explicit that some payment methods take 2–14 days to confirm, and that checkout.session.completed means the customer submitted the form, not the money arrived. If we ever enable BECS Direct Debit, firing the kitchen on completed would cook food for a payment that later fails.

Mitigation, from day one: restrict this flow to cards and wallets, and handle all three events — checkout.session.completed, checkout.session.async_payment_succeeded, checkout.session.async_payment_failed. Only flip orders.payment_status = 'paid' when session.payment_status === 'paid'.

Missing: the question that decides the architecture

She sent the Connect docs without asking who receives the guest's money. That single question determines whether this is a two-week build or a two-month one. Answered in §3.

Also, for the record

  • The email is addressed to "Sameer" and spells the brand "Biteperk". It is Sam and BitePerk.
  • She has biteperk.com.au only — no record of biteperk.com or the international locales.
  • She captured "will collect monthly subscription" (our SaaS billing) but not that we also intend to process guest payments. Those are different products with different fees and different risk profiles.

3. Money flow: Connect destination charges

Chosen Money lands in the BitePerk platform account and is immediately transferred to the venue's connected account, with BitePerk keeping a fee.

Stripe's own framing puts this squarely in the marketplace bucket — "customers transact with your platform for products or services provided by your connected accounts." The caller dialled a BitePerk number and spoke to Bella; from their point of view they transacted with us. Destination charges are the documented shape for that.

The exact call

// One Checkout Session. No Price, Product or Payment Link pre-created.
await stripe.checkout.sessions.create({
  mode: "payment",
  client_reference_id: order.id,                    // our UUID, ≤200 chars
  metadata: { order_id, restaurant_id, source: "voice" },
  expires_at: Math.floor(Date.now()/1000) + 30*60,  // 30 min — the floor Stripe allows
  line_items: order.items.map(i => ({
    quantity: i.quantity,
    price_data: {
      currency: "aud",
      unit_amount: i.unit_price_cents,              // already integer cents. No conversion.
      tax_behavior: "inclusive",                  // AU menu prices include GST
      product_data: { name: i.name_snapshot }
    }
  })),
  payment_intent_data: {
    transfer_data:        { destination: venue.stripe_connect_account_id },
    on_behalf_of:         venue.stripe_connect_account_id,
    application_fee_amount: feeCents(order.total_cents)
  },
  success_url: `${PUBLIC_WEB_BASE}/order/paid?session_id={CHECKOUT_SESSION_ID}`,
  cancel_url:  `${PUBLIC_WEB_BASE}/order/cancelled`
}, { idempotencyKey: `order-checkout:${order.id}:${order.version}` });

Why on_behalf_of as well as transfer_data.destination

It sets the venue as settlement merchant. Consequences, all of which we want:

  • The venue's name appears on the guest's card statement, not BitePerk's. Fewer chargebacks from "who is BitePerk?".
  • The venue's address and phone show on the statement.
  • Settlement happens in the venue's country and currency, under the venue's fee structure.
  • The Checkout page carries the venue's branding.

Caveat from the docs: on_behalf_of only works for connected accounts with a payments capability such as card_payments. Accounts under the recipient service agreement cannot have it. Our onboarding must request card_payments and transfers.

Region constraint — fine for us, worth knowing

Unless a platform is eligible for cross-border payouts, platform and connected account must be in the same region for a destination charge. BitePerk is an Australian entity onboarding Australian venues, so this is a non-issue today. It becomes one the day a New Zealand venue signs up.

The obligations we are taking on

Choosing this model is a business decision with regulatory weight, not an integration detail. Going in with eyes open:

  • Disputes hit the platform. For destination charges, with or without on_behalf_of, Stripe debits dispute amounts and fees from the platform account. If a guest charges back a $28 meal, BitePerk is out $28 plus the dispute fee until we reverse the transfer. We need charge.dispute.created handled and a transfer-reversal path.
  • Refunds default against us. Refunding a charge with transfer_data leaves the venue holding the transferred funds and the platform covering the negative balance — unless we pass reverse_transfer: true. Every refund path must set it, plus refund_application_fee per commercial policy.
  • Per-venue KYC. Every restaurant needs a connected account onboarded and verified before it can take a cent. This is real onboarding friction that lands in the wizard.
  • Negative-balance liability. Stripe asks platforms to choose who is responsible. Pick "Stripe responsible" unless there is a strong reason not to — it is the recommended default for platforms new to embedding payments.
  • Australian regulatory posture. Handling guest funds and remitting them is a different activity from billing venues for software. Whether it engages payment-facilitator or AFSL considerations is a question for an Australian financial-services lawyer, not for Stripe sales and not for this document. Get that advice before live mode. It does not block sandbox work.

Nothing here is a reason not to build it. It is a reason not to flip ORDER_PAYMENTS_ENABLED=true in production until the legal question has an answer.

4. The call, end to end

  1. Caller dials the venue number. Twilio → SIP trunk → Retell. Restaurant resolved from the dialled number by getRestaurantIdByDialedNumber, exactly as today. Caller-supplied restaurant_id is still ignored.
  2. Bella takes the booking via create_booking. Unchanged. An order still requires a reservation — create_order throws ORDER_REQUIRES_BOOKING without one.
  3. Bella takes the order via create_order. Fish and chips is matched against menu_items, priced, and written to orders + order_items inside one transaction. Returns order_id, order_number, confirmation_message. Unchanged.
  4. Bella offers to text a payment link. New. She asks — she does not assume. "I can text you a link to pay now, or you can pay when you arrive."
  5. Bella calls send_payment_link with the order_id and, optionally, a phone number the caller reads out. Backend creates the Checkout Session, stores it in order_payments, and enqueues an SMS in notifications_outbox — all in one transaction.
  6. Bella confirms out loud from the tool's confirmation_message: "Sent — it should arrive in a few seconds. The link's good for thirty minutes." She does not read the URL aloud.
  7. The SMS lands within ~5 seconds. notificationWorker ticks every 5 s and sends via Twilio.
  8. The caller taps and pays on Stripe's hosted page, branded as the venue.
  9. Stripe fires checkout.session.completed to POST /stripe/webhook. Signature verified, event deduped in stripe_webhook_events, advisory lock taken.
  10. We flip the order to paid — but only if session.payment_status === 'paid'. Writes orders.payment_status = 'paid' plus a payment_changed row in order_events.
  11. The kitchen sees it. KDS polls /api/orders/active every 2 seconds and already renders a PAID/UNPAID pill from order.payment_status. Zero KDS code changes. The pill flips within one poll.
If the caller has a withheld number. normalizePhone returns null for anonymous, unknown, private, blocked and restricted. The tool must return a graceful, spoken refusal — "I can't text a private number, but you can pay when you arrive" — not an error. Bella must never dead-air on this.

What we are deliberately not doing

  • No Stripe outbox worker. stripeClient.ts already documents a deliberate decision not to give Stripe the Cal.com circuit-breaker treatment — SDK retries, no outbox. Creating a session is synchronous inside a voice call; if Stripe is down, Bella says so and the caller pays at the venue. Adding a durable outbox would mean creating a payment link for a call that ended twenty minutes ago. Departing from the Cal.com pattern here is correct, and this paragraph is the justification.
  • No new SMS transport. Reuse notifications_outbox. It already has a lease, backoff and a Twilio sender.
  • No mid-call payment confirmation. Bella does not wait on the phone for the webhook. She says the link is sent and moves on.

6. Database — migration 030

The chain is append-only and currently runs to 029_least_privilege.sql. Next file is 030_order_payments.sql. Two hard rules from the existing codebase carry over: no GENERATED ALWAYS AS (node-pg 08P01), and migrations run as voxtable_owner, never postgres, or 029's ALTER DEFAULT PRIVILEGES silently strips voxtable_app grants from the new table.

-- 030_order_payments.sql
-- Voice-order payments via Stripe Checkout Sessions (Connect destination charges).

DO $$ BEGIN
  CREATE TYPE order_payment_status AS ENUM (
    'created',    -- session created, link not yet sent
    'sent',       -- SMS enqueued
    'processing', -- submitted, async method pending (BECS et al)
    'paid',
    'expired',
    'failed',
    'cancelled'
  );
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

CREATE TABLE IF NOT EXISTS order_payments (
  id                        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id                  UUID NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  restaurant_id             UUID NOT NULL REFERENCES restaurants(id) ON DELETE CASCADE,
  provider                  TEXT NOT NULL DEFAULT 'stripe',
  stripe_checkout_session_id TEXT,
  stripe_payment_intent_id  TEXT,
  stripe_connect_account_id TEXT,
  status                    order_payment_status NOT NULL DEFAULT 'created',
  currency                  TEXT NOT NULL DEFAULT 'aud',
  amount_cents              INTEGER NOT NULL CHECK (amount_cents > 0),
  application_fee_cents     INTEGER NOT NULL DEFAULT 0 CHECK (application_fee_cents >= 0),
  checkout_url              TEXT,
  recipient_phone           TEXT,               -- E.164, or NULL if withheld
  notification_id           UUID REFERENCES notifications_outbox(id) ON DELETE SET NULL,
  expires_at                TIMESTAMPTZ,
  created_at                TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at                TIMESTAMPTZ NOT NULL DEFAULT now(),
  sent_at                   TIMESTAMPTZ,
  paid_at                   TIMESTAMPTZ,
  last_error                TEXT,
  CHECK (application_fee_cents <= amount_cents)
);

-- One live attempt per order. Retries after expiry/failure are allowed.
CREATE UNIQUE INDEX IF NOT EXISTS idx_order_payments_active
  ON order_payments (order_id)
  WHERE status IN ('created', 'sent', 'processing');

CREATE UNIQUE INDEX IF NOT EXISTS idx_order_payments_session
  ON order_payments (stripe_checkout_session_id)
  WHERE stripe_checkout_session_id IS NOT NULL;

CREATE INDEX IF NOT EXISTS idx_order_payments_order ON order_payments (order_id, created_at DESC);

CREATE TRIGGER set_order_payments_updated_at
  BEFORE UPDATE ON order_payments
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();   -- helper from 001

-- The venue's Stripe connected account.
ALTER TABLE restaurants ADD COLUMN IF NOT EXISTS stripe_connect_account_id TEXT;
ALTER TABLE restaurants ADD COLUMN IF NOT EXISTS stripe_connect_charges_enabled BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE restaurants ADD COLUMN IF NOT EXISTS stripe_connect_payouts_enabled BOOLEAN NOT NULL DEFAULT false;

CREATE UNIQUE INDEX IF NOT EXISTS idx_restaurants_connect_account
  ON restaurants (stripe_connect_account_id)
  WHERE stripe_connect_account_id IS NOT NULL;

The partial unique index on order_id is the concurrency guarantee. If Retell double-fires the tool — which it does — the second insert hits a constraint violation and we return the existing link instead of creating a second Checkout Session. This is the same belt-and-braces posture as reservations_no_overlap: an advisory lock for politeness, a database constraint for correctness.

payment_changed is already a valid order_event_type and payment_status already has 'unpaid' | 'paid' | 'refunded'. Neither enum needs extending. Nice inheritance from the KDS work.

7. The payment service

src/services/orderPaymentService.ts. Shape follows orderService.createOrder: advisory lock, idempotency check, work, hydrate after commit.

export interface CreateOrderPaymentInput {
  restaurantId: string;
  orderId: string;
  recipientPhone?: string;   // caller-supplied override; else call.from_number
  actor: string;             // "voice:retell" | firebase uid
}

export async function createOrderPaymentLink(
  input: CreateOrderPaymentInput
): Promise<{ paymentId: string; checkoutUrl: string; expiresAt: Date;
             isReplay: boolean; confirmationMessage: string }>

Sequence

  1. Load the order via getOrderById(orderId, restaurantId). Tenant-scoped — a mismatch is a 404, never a cross-tenant read.
  2. Refuse politely if status === 'cancelled', payment_status === 'paid', or total_cents <= 0. All three return spoken sentences, not stack traces.
  3. Resolve the venue's stripe_connect_account_id. If absent or charges_enabled === false, return PAYMENTS_NOT_CONFIGURED with a spoken fallback: "This venue isn't set up for phone payments yet — you can pay when you arrive."
  4. Normalise the phone through utils/phone.ts. Null → graceful refusal.
  5. Call Stripe outside the transaction. A network call must never hold a Postgres connection open. Wrap in withStripeErrors("create_order_checkout_session", …) so rate limits and connection errors map to 503 BILLING_UPSTREAM_UNAVAILABLE like the rest of our Stripe surface. Pass a Stripe idempotencyKey of order-checkout:{orderId}:{version}.
  6. Then one withTransaction:
    • pg_advisory_xact_lock(hashtextextended('order_payment:' || orderId, 0))
    • Re-check for an existing active order_payments row → replay short-circuit
    • insertOrderPayment(...)
    • enqueueNotification({ channel: 'sms', kind: 'order_payment_link', … }, db) — same txn
    • insertOrderEvent({ eventType: 'payment_changed', from: 'unpaid', to: 'link_sent', actor, metadata }, db)
  7. After commit, build the spoken confirmation. Never include the URL — Bella must not read a Stripe URL aloud.
Ordering hazard. Stripe call before transaction means a crash between the two leaves an orphan Checkout Session in Stripe with no local row. That is acceptable — the session expires in 30 minutes and was never sent to anyone. The reverse ordering (transaction first, Stripe call inside) would hold a DB connection across a network call under voice-path latency. Take the orphan.

Fee calculation

Keep it in one exported, unit-testable function so the commercial rate is never scattered:

// services/orderPaymentService.ts
export function platformFeeCents(totalCents: number): number {
  const pct  = env.ORDER_PAYMENT_FEE_BPS / 10_000;   // basis points
  const flat = env.ORDER_PAYMENT_FEE_FLAT_CENTS;
  return Math.min(totalCents, Math.round(totalCents * pct) + flat);
}

The Math.min is not decoration — Stripe caps application_fee_amount at the transaction total and errors above it. On a $6 side of chips a percentage-plus-flat fee can approach the total.

9. Getting the link to the phone

Two blockers, both real, both fixable

Blocker 1 — no Twilio number that can send SMS

Per CLAUDE.md, verified in the Twilio console on 10 Aug 2026: an Australian Local 02 number is voice-only and cannot send SMS at all. Only a Mobile +61 4 number does both voice and SMS, at A$8.25/mo versus A$3.00/mo. There is no single geographic number that answers calls and texts.

Action: buy a Mobile +61 4 number in Biteperk-staging and set it as NOTIFICATIONS_SMS_FROM. Voice stays on the existing number. Prove it in staging, then repeat in production — Twilio has no promote, and the two accounts look nearly identical in the console, so check the account picker before every change.

Blocker 2 — SMS is gated behind an email credential

services/notificationService.ts:

export function isNotificationsEnabled(): boolean {
  if (!env.NOTIFICATIONS_ENABLED) return false;
  return env.EMAIL_PROVIDER === "zeptomail"
    ? Boolean(env.ZEPTOMAIL_TOKEN)
    : Boolean(env.SENDGRID_API_KEY);
}

startNotificationWorker() returns early unless this is true. So with NOTIFICATIONS_ENABLED=true and no SendGrid/Zepto key, the whole worker no-ops and the SMS is never sent — silently, with no error anywhere.

Fix: split the predicate. isEmailEnabled() keeps the current logic; isSmsEnabled() checks TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN and NOTIFICATIONS_SMS_FROM. The worker starts if either is true and skips rows whose channel is disabled. Small change, and it must land before anything else in this plan is testable end to end.

Third change: transactional enqueue

enqueueNotification currently uses a bare pool.query, does not accept a DbClient, and returns Promise<void>. Two changes, matching enqueueOutbox:

export async function enqueueNotification(
  input: EnqueueNotificationInput,
  db: DbClient = pool                     // ← add: lets it join our txn
): Promise<string>                        // ← add: RETURNING id, for order_payments.notification_id

The DbClient parameter is what stops a crash between the order_payments insert and the SMS enqueue leaving a payment row nobody was told about. The return value is what populates order_payments.notification_id, so a failed SMS is traceable back to the payment it belonged to. Both are additive and backwards-compatible with the five existing call sites.

Message copy

Alphanumeric sender IDs are one-way, so no copy may invite a reply. Even on a mobile number, write as though replies are impossible — it keeps the copy portable when the ACMA BitePerk sender ID lands.

Natalia's Bistro — order #14, $28.50.
Pay here: https://checkout.stripe.com/c/pay/cs_test_…
Link expires in 30 minutes. Do not reply to this message.

Venue name first — the guest called the restaurant, not us. This is the venue-is-the-hero rule in a 160-character box.

Latency

notificationWorker ticks every 5 s with a batch of 10. An SMS enqueued mid-call goes out within roughly 5 seconds — comfortably inside a call where Bella is still confirming details. There is no synchronous send path and we should not build one: a direct Twilio call from the Retell tool handler would put a third-party network call on the voice path's critical latency budget. Five seconds is fine. Bella says "it's on its way", not "it's arrived".

Fourth change (shipped 6 Sep 2026): a receipt text once the payment lands

Stripe has no SMS receipt, and its Customer emails → Successful payments toggle was off for the live Biteperk account until 6 Sep 2026, so before this the guest heard nothing after paying. On the paid webhook the backend now fetches the charge's hosted receipt_url and texts it to the number the link went to, kind order_payment_receipt, one-way copy. Once-only is structural: markOrderPaidIfUnpaid gates every redelivery and order_payments.receipt_notification_id (migration 043) is the second belt, written in the same transaction. A failed receipt look-up is never fatal — the text goes without a link — because a 500 would make Stripe redeliver a payment we already hold. Nothing is sent on amount mismatch, paid-after-cancel or async-pending.

Guests get text + email (decision 6 Sep 2026). Stripe Checkout always collects an email, so with the live toggle ON every payer receives Stripe's email receipt as well as our text, and the /order/paid page promises both. The sandbox account has its own independent toggle. Before enabling ORDER_PAYMENTS_ENABLED in production, read the live toggle back in the dashboard — the page copy must never promise an email that live mode will not send. Refund texts are a separate follow-up.

Fifth change (6 Sep 2026): short branded links in both texts

The link text carried a ~400-character Stripe Checkout URL and the receipt text a ~110-character receipt URL — unreadable, three and two SMS segments. Each payment row now mints an unguessable public_token (16 random bytes, base64url, migration 044) and the texts carry /pay/<token> and /receipt/<token> on PUBLIC_ORDER_RETURN_BASE_URL. Firebase Hosting rewrites those two paths to the environment's Cloud Run API (injected by deploy-frontend.yml, never committed, with a stg/prod mismatch guard), and the API answers 302: to Checkout while the row is live, to /order/paid once paid, otherwise to /order/expired. Unknown, malformed and expired tokens all land on the same page, so a response never says whether a token exists. Rate-limited per IP; the token and the Stripe URL are never logged. The token is deliberately not the order id: order ids show in the KDS, the dashboard and Retell transcripts, while a checkout URL is a live pay capability and the receipt shows card last-4 and items. Both texts now fit one GSM segment.

Production needs PUBLIC_ORDER_RETURN_BASE_URL=https://voxtable.biteperk.com.au in the prod Terraform map before payments are enabled there (see the rollout checklist).

10. Webhooks and reconciliation

The single most dangerous line in this plan

handleBillingWebhook in stripeService.ts already handles checkout.session.completed and maps it unconditionally to subscription_active. And its attribution helper reads metadata first:

// stripeService.ts:476 — restaurantIdForEvent
const metaId = (object.metadata as Record<string, unknown> | undefined)?.restaurant_id;
if (typeof metaId === "string" && metaId) return metaId;   // ← first match wins
const ref = object.client_reference_id;
if (typeof ref === "string" && ref) return ref;

Our session carries metadata.restaurant_id. So without a branch this is not a hypothetical collision — it is guaranteed: a guest paying for fish and chips would attribute to the venue and flip its SaaS subscription to active, skipping the trial. Branch on session.mode as the very first statement in that handler, before restaurantIdForEvent is ever called.

case "checkout.session.completed":
case "checkout.session.async_payment_succeeded":
case "checkout.session.async_payment_failed": {
  const session = event.data.object as Stripe.Checkout.Session;

  // Belt: mode. Braces: our own metadata marker.
  const isOrderPayment =
    session.mode === "payment" && session.metadata?.biteperk_kind === "order_payment";

  if (isOrderPayment) return handleOrderPaymentWebhook(event, session);
  // …existing subscription handling, unchanged…
}

The order-payment handler

  1. Look up order_payments by stripe_checkout_session_id. Unknown session → log and return 200. Never 500 on an event we don't recognise; Stripe would retry forever.
  2. Check session.payment_status === 'paid' before flipping anything. On completed with payment_status: 'unpaid' (async method pending), set our row to processing and leave the order unpaid. The kitchen does not cook on a promise.
  3. Reconcile session.amount_total against order_payments.amount_cents. A mismatch means the order changed after the link was sent — log loudly, do not auto-resolve.
  4. Flip orders.payment_status = 'paid', write a payment_changed event, stamp paid_at and stripe_payment_intent_id. One transaction.
  5. Return 200. The existing route already handles dedupe via stripe_webhook_events, the advisory lock via withAdvisoryLock, and the status contract (400 bad signature, 500 to trigger Stripe retry, 200 on success or duplicate).

The version-conflict trap

updatePaymentStatus in orderService.ts demands an expectedVersion and throws VERSION_CONFLICT — correct for the staff If-Match path, wrong for a webhook that has no version in hand. Do not reuse it. Add a sibling, markOrderPaidFromWebhook(orderId, restaurantId, paymentIntentId, db), that reads the current version inside the transaction. A webhook must not fail because a waiter touched the order in the intervening two seconds.

Refunds

Whenever we build the refund path, both flags are mandatory or the money ends up in the wrong place:

await stripe.refunds.create({
  charge: chargeId,
  reverse_transfer: true,        // pull funds back from the venue
  refund_application_fee: true   // or false, per commercial policy
});

Without reverse_transfer, the venue keeps the money and BitePerk eats the refund.

14. Testing

House rule: product behaviour is smoke-tested, not unit-tested. DB-free node:test units are allowed for pure plumbing. No Jest. Every smoke, fixture, payment and call test in this section runs only in staging. Production receives no dummy/seed data and no state-changing test.

Unit — DB-free, runs in npm run check

  • platformFeeCents — including the cap where fee ≥ total.
  • Line-item mapping: our order_items → Stripe price_data, including a variant and a modifier, asserting the summed unit_amount matches line_total_cents.
  • SMS body builder: length, no reply invitation, venue name present, URL present.
  • Env schema: ORDER_PAYMENTS_ENABLED=true with missing credentials must fail to boot.

scripts/smoke-payments.ts → npm run smoke:payments

  1. Seed a reservation and an order with a known total.
  2. POST /retell/tools/send-payment-link; assert sent: true, a confirmation_message, and no URL in the response body.
  3. Assert exactly one order_payments row and one notifications_outbox row with channel = 'sms'.
  4. Call the tool again — assert is_replay: true and still exactly one row each. This is the double-fire test and it is the one that matters.
  5. Replay a signed checkout.session.completed fixture; assert orders.payment_status = 'paid' and one new payment_changed event.
  6. Replay the same event; assert no duplicate event row (webhook dedupe).
  7. Replay a completed with payment_status: 'unpaid'; assert the order stays unpaid and order_payments.status = 'processing'.
  8. Replay a subscription-mode checkout.session.completed; assert onboarding status changes and no order is touched. The cross-contamination guard.

Manual, once per phase

  • Real call → real SMS → real sandbox payment → KDS pill flips. Nothing substitutes for this.
  • Withheld caller ID: dial with #31# prefix and confirm Bella degrades gracefully.
  • Let a link expire; confirm checkout.session.expired lands and a resend is possible.

GST — worth an accountant's five minutes

Australian menu prices include GST, so line items go out as tax_behavior: "inclusive". With on_behalf_of the venue is the settlement merchant, which is the right posture for GST liability — the venue sold the meal, not BitePerk. Do not enable automatic_tax on this flow without confirming that reading. Our subscription Checkout path already uses automatic_tax: { enabled: true }; the two flows have different tax answers and should not share configuration.
