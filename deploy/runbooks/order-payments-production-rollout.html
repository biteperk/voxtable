The three things that change the plan

I re-read the merged branch and the infrastructure state before writing this. Three findings reshape the rollout, and one of them is a security issue that is not in the PR.

1. The log redaction for checkout session ids is uncommitted

apps/backend/src/utils/logger.ts is modified in your working tree but the change is in no commit, so it is not in PR #154:

$ git diff --stat apps/backend/src/utils/logger.ts
 apps/backend/src/utils/logger.ts | 5 ++++-
$ git log --oneline -1 -- apps/backend/src/utils/logger.ts

The change adds checkouturl to SENSITIVE_KEY_PATTERN and a redaction pattern for cs_(test|live)_…. Your own comment on it explains why it matters: "the id IS the payment page URL suffix — a logged cs_… is a live 'pay this order' capability until the session expires."

Without it, every checkout session id lands in Cloud Logging in plaintext, and anyone with log read access can pay — or re-pay — a guest's order for 45 minutes. Commit it to the PR branch before merge. CLAUDE.md, README.md and deploy/runbooks/acma-sender-id-registration.md are also uncommitted or untracked and should go in the same push.

2. Environment correction

This is a historical rollout plan. Production is Cloud Run and Cloud SQL in bp-voxtable-prod. core-central-vm is sandbox-only; none of its code, configuration or data may be deployed or migrated to production.

A CI-green promotion to main deploys the Cloud Run production services and runs the production migration job before the services roll.

Code

Close the code gaps that only matter with real money

Engineering~3 days

Four things were consciously deferred. Three of them are fine to defer in a sandbox and are not fine in production, because they only bite when the money is real.

1.1 Refunds — must have

grep -rn "reverse_transfer\|refunds.create" apps/backend/src/ returns nothing. Today charge.refunded is observed but never initiated, so every refund is a manual click in the Stripe dashboard — and a dashboard refund does not reverse the transfer. The venue keeps the money and BitePerk absorbs the refund. On a $28 meal that's an annoyance; as a standing policy it's a slow bleed.

Build refundOrderPayment() with reverse_transfer: true hard-coded, not a parameter. Make refund_application_fee the only policy decision. Expose it to managers only. Until it exists, write the manual procedure into the day-one runbook — refund in the dashboard and reverse the transfer, as two deliberate steps.

1.2 Log redaction — must have

Commit it. Covered above.

1.3 charge.updated / skipped transfers — should have

If a venue loses its transfer capability mid-flight, Stripe skips the transfer and the funds stay in our balance with transfer_data: null on the charge. Nobody is told. One handler and a Slack alert; an hour's work that prevents a silent money-in-the-wrong-place condition.

1.4 The reaper's blind spot — should have

The reaper is deliberately not gated on ORDER_PAYMENTS_ENABLED — correct, because links already in guests' hands must keep settling after a kill switch. But getStripe() throws BILLING_NOT_CONFIGURED unless STRIPE_BILLING_ENABLED or ORDER_PAYMENTS_ENABLED is on. So in the exact scenario the design anticipates — flag flipped off with links outstanding — every reap logs order_payment_reap_failed and settles nothing. Either widen the entitlement or make the failure loud rather than per-row noise.

Exit criteria A refund issued through our own code path reverses the transfer, verified in the Stripe sandbox balance. No cs_test_ string appears anywhere in staging logs after a full payment cycle (gcloud logging read, grep it — do not assume).

Legal

Australian financial-services advice

SamHard blockWeeks — start now

This is the only gate that can stop the whole thing, and the only one where the lead time is entirely outside your control. Start it this week even though nothing else waits on it.

I am not a lawyer and this is not legal advice. What follows is a brief for one — the vocabulary and the specific facts that will let a specialist answer quickly instead of billing you to discover them.

The question, precisely

Not "do we need an AFSL". The question is: does taking a guest's card payment into the BitePerk Stripe account and immediately transferring it to the venue's connected account constitute a regulated payment function, and if so does an exemption apply?

The facts that make our position stronger than it looks

  • We hold no float. Destination charges transfer to the venue's pending balance immediately on capture. There is no stored value, no wallet, no preloading, no guest balance. Much of the Australian regulatory concern is about facilities where users load and retain funds — that is not this.
  • The venue is the settlement merchant. We set on_behalf_of, so the venue's name is on the guest's statement, settlement is in the venue's country and currency, and the venue's fee structure applies.
  • Stripe holds the funds, not us. Stripe is the licensed party in the flow.
  • Single-use, purchase-specific. Each link is one order, expires in 45 minutes, and cannot be topped up or reused.

The facts that create exposure

  • Funds transit an account in BitePerk's name, however briefly.
  • We take an application_fee_amount from a third party's transaction.
  • Disputes and refunds debit the BitePerk account, so we carry settlement risk.
  • Australia's payments reforms have been extending licensing from the older "non-cash payment facility" framing toward defined payment functions including payment facilitation, with prudential oversight where significant customer funds are held. The ground has moved recently; a 2023 answer may not be a 2026 answer.

Ask counsel these five

  1. Does destination-charge flow-through, with no float and the venue as settlement merchant, engage an AFSL requirement — and has that answer changed under the current payments reforms?
  2. If it does, does the low-value relief instrument apply at our volumes, and what are the thresholds we must monitor so we know before we cross one?
  3. Does the application_fee_amount change the characterisation?
  4. Is there any AUSTRAC or remittance registration exposure?
  5. What contractual terms must be in the venue agreement — who bears chargebacks, refund authority, and what we must disclose to the guest?

Question 5 is the sleeper. Our venue agreement (the agreement_acceptances ledger, rev. 29 Jul 2026) predates this feature entirely and says nothing about handling guest money. It will need an amendment, which means a new Order Form election and probably re-acceptance by existing venues. That is product work with its own lead time — surface it early.

Exit criteria Written advice from an Australian financial-services lawyer, naming the specific structure. Plus a drafted venue-agreement amendment covering chargeback liability and refund authority.

Stripe

Stripe live mode and the Connect platform profile

SamDays
  • Complete the live Connect platform profile. Separate from the sandbox one. Stripe reviews it.
  • Choose negative-balance responsibility: Stripe. The recommended default for platforms new to embedding payments — Stripe monitors connected accounts for credit and fraud risk and handles remediation directly. Choosing "platform responsible" means we own that operationally, and we have no team for it.
  • Register the live webhook endpoint and subscribe to all seven events the code now handles: checkout.session.completed, .async_payment_succeeded, .async_payment_failed, .expired, charge.refunded, charge.dispute.created, account.updated. Note: account.updated for connected accounts arrives on the Connect webhook endpoint, not the account one — a separate endpoint in the dashboard. Miss it and venues will onboard successfully while stripe_connect_charges_enabled stays false forever, and every payment attempt returns PAYMENTS_NOT_CONFIGURED with no obvious cause.
  • Set the live STRIPE_WEBHOOK_SECRET. Different from test. This is the single most common live-mode mistake and it presents as 400s on every webhook.
  • Set the platform fee deliberately. ORDER_PAYMENT_FEE_BPS and ORDER_PAYMENT_FEE_FLAT_CENTS both default to 0 — ship the pilot at zero on purpose, then set it once you have real basket sizes. Remember our net is application_fee − stripe_processing_fee, so a fee below roughly 1.7% + 30¢ is loss-making.
  • Confirm the 1 Oct 2026 AU rate in writing before setting the fee. Take the eight questions from the prior plan to the 19 August Sydney session.
Exit criteria Live platform profile approved. Both webhook endpoints registered and receiving. One live connected account onboarded end to end (the pilot venue) with charges_enabled = true synced into our database by the webhook, not by hand.

Bella

Register the tool and write the prompt

Engineering~1 day

The backend route exists. Nothing in the repo registers the tool with Retell — no tool definition in deploy/retell-snapshots/, and no prompt text telling Bella when to call it. Until this is done the feature is unreachable by voice, no matter what the flags say.

  • Snapshot first — deploy/retell-snapshots/<timestamp>-add-payment-link/{llm.json,agent.json}. This is the rollback for a bad prompt.
  • Register send_payment_link in the Retell dashboard: URL, JSON schema matching sendPaymentLinkRetellSchema, description.
  • Prompt rules, non-negotiable:
    • Offer, never assume. "Would you like me to text you a payment link, or would you rather pay when you arrive?"
    • Never read a URL aloud. The tool response deliberately omits the checkout URL so the model cannot leak what it never sees — but the prompt must also stop it from inventing one.
    • Read back the number digit by digit if the caller gives one.
    • Say the expiry: "The link's good for forty-five minutes."
    • Every refusal has a spoken fallback — withheld number, venue not set up, payments disabled all end with "you can pay when you arrive." No dead air.
  • Ten scripted calls on staging before the pilot: happy path, decline, withheld number, caller changes the order after the link is sent, caller asks Bella to read the link aloud (she must refuse), caller asks to resend.
Exit criteria Ten scripted staging calls pass, including the refusals. Snapshot committed. A colleague who has not seen the prompt cannot get Bella to read a URL out loud.

Day-one runbook

Pin this where whoever is on call can find it. It assumes Gate 7 step 3 has just happened.

Guest says they paid, ticket says UNPAID

  1. Stripe dashboard → Payments → search the guest's phone or the amount. If there is no payment, they haven't paid — the link may have expired.
  2. If there is a payment: the webhook was missed. Wait five minutes — the reaper reconciles against Stripe as the source of truth and will flip it. This is exactly what it's for.
  3. Still unpaid after ten minutes: check the webhook endpoint in Stripe for delivery failures. 500s mean "row missing" and self-heal on retry; 400s mean the webhook secret is wrong and nothing will self-heal.
  4. Never flip payment_status by hand in SQL. Fix the webhook; let the system converge.

Guest wants a refund

Until Gate 1.1 ships, this is two steps and doing only the first is a silent loss:

  1. Stripe dashboard → the payment → Refund.
  2. Then reverse the transfer — dashboard → Connect → Transfers → find the transfer for that charge → reverse. Without this the venue keeps the money and BitePerk covers the refund.

Amount mismatch alert

The guest paid a different amount than the order total — usually the order was edited after the link was sent. The money is recorded, the order deliberately stays unpaid, and a human decides. Never auto-resolve. Refund the difference or take the balance at the venue.

Guest paid a cancelled order

The payment is recorded, the order stays cancelled, nothing is cooked, and staff are alerted. Refund it in full, both steps.

Kill it

ORDER_PAYMENTS_ENABLED=false, redeploy. New links stop immediately; Bella falls back to "you can pay when you arrive." Links already sent keep settling — the reaper and webhooks are deliberately not gated on the flag. Check Gate 1.4 first: if that entitlement bug is unfixed and STRIPE_BILLING_ENABLED is off, the reaper will fail every row after the flip.

Add one business metric that no alert covers: link-to-payment conversion. If guests receive links and don't pay them, the mechanism works and the product doesn't. That is the number that tells you whether to keep building.

Rollback and abort

Three levels, in order of preference

  1. Flag flip — ORDER_PAYMENTS_ENABLED=false. Seconds. Stops new links, lets outstanding ones settle. This is the rollback for almost everything.
  2. Revision rollback — move Cloud Run traffic to the previous healthy revision. Minutes. Use this for a code regression; the sandbox VM is never a production rollback target.
  3. Schema rollback — there is no down migration for 030 and you almost certainly don't want one. The table is additive; leaving it is harmless. If you truly must, the ordering is order_payments → the restaurants columns, and the ON DELETE RESTRICT foreign keys will fight you.

Abort criteria — stop the pilot immediately

  • Any guest charged twice for one order.
  • Any payment that cannot be traced to a transfer within 24 hours.
  • Any order cooked and served that was never paid, where the system said PAID.
  • Two or more disputes in the pilot window.
  • Legal advice arrives and contradicts the structure.

Aborting is a flag flip and a phone call to Natalia's. Cheap. The expensive thing is discovering any of the above from an angry guest instead of from an alert — which is what the monitoring above is for.

Money reconciliation

Nobody plans this and everybody needs it in week two. Weekly, during the pilot; monthly after.

  1. Export Stripe balance history for the period.
  2. SELECT sum(amount_received_cents) FROM order_payments WHERE status = 'paid' AND paid_at BETWEEN …
  3. Those two must agree. If they don't, the difference is either a payment we never recorded (webhook lost and reaper failed — investigate hard) or a Stripe-dashboard payment created outside our code (carries no biteperk_kind marker, so our webhook branch ignores it entirely — this is why hand-creating payments in the live dashboard is a bad habit).
  4. Sum application fees collected; compare to sum(application_fee_cents).
  5. Confirm each venue's transfers match their orders. Give venues a statement they can check — they will check, and being able to answer is the difference between a trusted product and a suspicious one.
